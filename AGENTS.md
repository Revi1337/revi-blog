## Fonts
- **Inter** — body text (`body-md`) only
- **JetBrains Mono** — labels/code/meta info (`label-caps`, `code-sm`): nav, buttons, badges, dates, tags, TOC, code blocks, footer
- **SUIT** — Hangul-only fallback for both of the above. Inter/JetBrains Mono are Latin-only subsets with no Hangul glyphs, so `--font-body-md`/`--font-label-caps`/`--font-code-sm` in `app/globals.css` list SUIT second (`Inter, SUIT, sans-serif` / `JetBrains Mono, SUIT, monospace`) — Latin characters still resolve to Inter/JetBrains Mono, only Hangul falls through to SUIT. Loaded via `next/font/local` in `app/layout.tsx` as `--font-suit`, self-hosted as static woff2 files (400/500/600/700) under `public/fonts/suit/` (sourced from `sunn-us/SUIT`, OFL-licensed — no npm package).
- **Pretendard** — headings only (`headline-xl`, `headline-lg`, `headline-lg-mobile`). Mixing Inter (Latin) + SUIT (Hangul) in one heading (e.g. "Python 코드") produces mismatched visual weight even at the same numeric `font-weight`, because the two typefaces are drawn independently. Pretendard's Latin glyphs are designed to sit naturally alongside its Hangul glyphs, so headings use Pretendard alone instead of the Inter+SUIT pair. Loaded via `next/font/local` as `--font-pretendard`, self-hosted as static woff2 (600/700 only — the two weights headings actually use) under `public/fonts/pretendard/` (sourced from `orioncactus/Pretendard`, OFL-licensed — static files, not the variable-font npm package).

Applies consistently across all 4 screens (`core/home-dark.html`, `core/home-light.html`, `core/article-detail-dark.html`, `core/article-detail-light.html`). Do not mix in other font families beyond Inter/JetBrains Mono/SUIT/Pretendard (e.g. Geist).

## Upstash Redis (visitor/view stats)
- **Environment variables**: `lib/stats/redis.ts` reads `KV_REST_API_URL`/`KV_REST_API_TOKEN` directly instead of `Redis.fromEnv()` — the Vercel Marketplace-connected Upstash generates env vars named `KV_REST_API_*`, not `UPSTASH_REDIS_REST_*`. Don't put the real values in `.env.local` — that file loads during `next dev` too, so local dev would share the live production Redis instance. If you need the real values locally (e.g. to run a production-mode build), pull them into `.env.production.local` instead (`vercel env pull --environment=production .env.production.local`), which only loads under `NODE_ENV=production` (`next build`/`next start`).
- **Don't move the counting logic back into middleware (`proxy.ts`)**: middleware previously tried to filter out prefetch requests by header, but Next strips all FLIGHT_HEADERS (e.g. `next-router-prefetch`) right before invoking middleware (`node_modules/next/dist/server/web/adapter.js`), making this structurally impossible to distinguish. Counting was moved to `app/api/track` (called on client component mount) instead.
- **Runtime split**: `/api/track` (writes) runs on the Node runtime — it needs slug existence validation (`getArticleBySlug`, `fs`-based). `/api/stats`, `/api/stats/[slug]` (reads) run on the Edge runtime (avoids cold starts), so they skip that validation and return a view count of 0 even for a slug that doesn't exist.
- **"Today" is always KST-based**: go through `getKstDateString()`/`getKstYesterdayDateString()` in `lib/stats/get-stats.ts` — the server's clock runs in UTC, so comparing `new Date()` directly shifts the date by a day near midnight.
- **In-memory fallback for local dev**: if `KV_REST_API_URL` is absent, `lib/stats/redis.ts` automatically switches to the in-memory mock in `lib/stats/local-redis.ts` (the Upstash Vercel Marketplace integration only allows one free DB per account, so a second, local-only instance would incur cost — we chose not to create one). `eval()` reimplements the exact same GET/SET EX/INCR/SET EX NX logic as `lib/stats/scripts/track-visit.lua` in JS, so if the Lua script changes, `local-redis.ts` must be updated to match. **Known limitation**: because this in-memory store lives inside one JS module instance and `/api/track` (writes) runs on the Node runtime while `/api/stats`/`/api/stats/[slug]` (reads) run on the Edge runtime, `next dev` executes them in separate isolates that don't share this memory — writes succeed but the widget always displays `0`. This isn't a bug; it just means the in-memory path can't be used to visually verify counts incrementing. Use the Docker Redis setup below when you need that.
- **Docker Redis for local end-to-end verification**: `npm run dev` never touches Docker on its own — it stays on the zero-setup in-memory mock unless you opt in with `npm run dev:docker`. `docker-compose.yml` runs `redis:7-alpine` plus `hiett/serverless-redis-http` (Upstash's official REST-API-compatible proxy — `@upstash/redis` only speaks REST, not the raw RESP protocol, so a plain Redis container isn't enough on its own). Being a real external Redis, it isn't scoped to one runtime, so `/api/track` writes and `/api/stats` reads see the same state — the widget increments correctly, and the real `track-visit.lua` executes instead of the JS reimplementation.

  `npm run dev:docker` does everything in one command: starts the containers (`docker compose up -d`, requires Docker Desktop running), `export`s the two vars from `.env.local-dev` (gitignored, not checked in — recreate it locally with `KV_REST_API_URL=http://localhost:8079` and `KV_REST_API_TOKEN=local-dev-token`, matching the SRH container's port/token in `docker-compose.yml`) into the shell, then launches `next dev`. Since `process.env` outranks every `.env*` file in Next.js's lookup order, this overrides whatever `.env.local` has without editing that file at all. Plain `npm run dev` (no env vars set this way) falls straight back to the in-memory mock.

  (We tried `node --env-file=.env.local-dev` first since it's the more idiomatic way to point Node at an arbitrary env file — it doesn't work here because `next dev` propagates flags to its Turbopack/webpack worker subprocesses via `NODE_OPTIONS`, and `--env-file` is one of the flags Node explicitly disallows inside `NODE_OPTIONS`. The `export $(cat ...) &&` shell approach sidesteps that entirely by setting real env vars before `next` ever starts, with no new dependency needed.)

  Data persists across `next dev` restarts as long as the containers stay up (it's a real external process, not in-process memory) — only `npm run redis:down` or `docker compose down` clears it. This is entirely local and never touches the real (production) Upstash instance.

## ⚠️ IMPORTANT: `content/articles/**` changes require a `next dev` restart
`lib/data/articles.ts` loads all markdown via a **top-level `await loadArticles()`**, which runs once when the module is first evaluated and caches the parsed result (including the rendered HTML) for the life of the process. `loader.ts` reads `.md` files with `fs.readFileSync`, which is invisible to Turbopack/webpack's import-graph-based file watcher — so editing anything under `content/articles/` does **not** trigger Fast Refresh, unlike component/CSS changes.

**A browser refresh alone will never show the change.** To verify any edit to `content/articles/**` (including nested dirs like `content/articles/algorithm/`), you must kill the running `next dev` process and start it again — only then does the top-level await re-run and re-render the markdown. This applies whether the edit is frontmatter, body text, or a plugin-affecting change (callouts, images, code fences, etc.).

## iOS Safari: the notch/status-bar strip and `backdrop-filter`
The NavBar is a glassmorphic `fixed` header (`bg-background/70` + `backdrop-blur-md`). On iPhone, the strip behind the status bar kept showing the **previous** theme's color after toggling dark/light — it only caught up on device rotation or a page reload.

**Root cause: `backdrop-filter` freezes iOS Safari's top-color sampling.** Safari paints that strip by sampling the pixels the page draws at the top of the viewport. When the topmost element has `backdrop-filter`, that sampling goes stale and is not refreshed by a style-only change (a class toggle); only a relayout (rotation) or reload refreshes it.

Three assumptions cost several failed attempts before a real device disproved them:
- **`env(safe-area-inset-top)` is `0` in a normal Safari tab** — the web view does not extend under the notch (it is non-zero only in standalone/PWA mode). Any `pt-[env(safe-area-inset-top)]` on the header is therefore a no-op in the browser; it is kept only for the standalone case.
- **Safari samples painted pixels, not `<meta name="theme-color">`** — a test page whose `theme-color` never changed still updated the strip correctly, so `theme-color`/`color-scheme` cannot drive this.
- **Transparency is irrelevant.** Measured on-device: opaque+no-blur = OK, translucent+no-blur = OK, opaque+blur = broken, translucent+blur = broken. Only blur matters.

**The fix** (`theme-context.tsx` + `nav-bar.tsx`): when the theme toggles, drop `backdrop-blur` for ~2 frames so one blur-free frame is painted, letting Safari re-sample, then restore it. Two details are load-bearing:
- The color change and the blur removal must happen in the **same event handler** (React batches them into one render, so the new color and the missing blur are painted in the same frame), and the restore must go through **two nested `requestAnimationFrame`s** — toggling a value off and back on within one frame paints no intermediate state at all and is a no-op.
- The header's transition must be **`transition-colors`, never `transition-all`**, and transitions must be **disabled entirely while the blur is suppressed**. With a 200ms color transition the blur-free frame (~33ms) still shows the *old* background color, so Safari re-samples the wrong value and the workaround silently does nothing.

**Methodology note — this was diagnosed the wrong way for six rounds.** The failures all came from reasoning about iOS behavior from a machine with no iPhone, shipping a guess, and asking whether it worked. What finally settled it was building a throwaway diagnostic route that emulated the header under controlled variants (opaque/translucent × blur/no-blur, plus candidate workarounds) and having it exercised on the actual device, which isolated the single responsible property in one pass. **When a bug is device-specific and cannot be reproduced locally, build the diagnostic harness first instead of iterating on inferences.**
