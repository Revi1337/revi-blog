# Feature Specification: FlexSearch 검색 엔진 마이그레이션

**Feature Branch**: `[007-flexsearch-search-migration]`

**Created**: 2026-07-21

**Status**: Draft

**Input**: User description: "아티클 검색(SearchBar)과 홈페이지 QuickSearch 태그 필터의 매칭 엔진을 네이티브 substring 구현에서 flexsearch 라이브러리(https://github.com/nextapps-de/flexsearch) 기반으로 교체한다. 사용자에게 보이는 검색 결과와 UI/UX는 기존과 완전히 동일하게 유지해야 한다 — 신규 기능이 아니라 내부 엔진 교체다."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 헤더 텍스트 검색 결과 동일성 (Priority: P1)

방문자가 헤더의 Ctrl+K 검색을 열어 제목/본문에 포함된 단어를 입력하면, 매칭 엔진이 바뀌기 전과 동일한 아티클이 동일한 순서(제목 매치 우선, 그 다음 본문 매치, 각 그룹 내부는 발행일 내림차순)로 나타난다.

**Why this priority**: 텍스트 검색은 SearchBar의 가장 기본적이고 사용 빈도가 높은 경로이며, 결과가 하나라도 달라지면 "동일하게 유지"라는 이번 작업의 핵심 전제가 깨진다.

**Independent Test**: 마이그레이션 전 결과를 스냅샷으로 남겨두고, 동일한 검색어 집합(단일 단어, 대소문자 혼용, 제목에만 있는 단어, 본문에만 있는 단어)을 마이그레이션 후 UI에 입력해 결과 목록과 순서를 비교하는 것만으로 독립적으로 검증 가능하다.

**Acceptance Scenarios**:

1. **Given** 여러 아티클의 제목과 본문에 서로 다른 단어가 흩어져 있는 상태, **When** 방문자가 제목에만 존재하는 단어를 입력하면, **Then** 그 단어를 제목에 포함한 아티클만 상단에 표시되고 본문 매치는 표시되지 않는다.
2. **Given** 어떤 단어가 한 아티클의 제목에, 다른 아티클의 본문에 각각 등장하는 상태, **When** 방문자가 그 단어를 검색하면, **Then** 제목 매치 아티클이 본문 매치 아티클보다 항상 위에 표시된다.
3. **Given** 검색어와 대소문자가 다른 단어가 본문에 포함된 상태, **When** 방문자가 소문자로 검색하면, **Then** 대소문자와 무관하게 매치되어 결과에 나타난다.

---

### User Story 2 - 헤더 태그 검색 결과 동일성 (Priority: P2)

방문자가 `#태그명`으로 태그 검색을 하거나 공백으로 여러 태그를 이어 입력하면, 마이그레이션 전과 동일한 아티클 집합이 랭킹 없이 원래 순서 그대로 나타난다.

**Why this priority**: 태그 검색은 텍스트 검색과 매칭 규칙(AND, substring)이 달라 별도로 검증해야 하는 독립적인 경로이지만, 텍스트 검색만큼 자주 쓰이지는 않아 P1보다 우선순위가 낮다.

**Independent Test**: 단일 태그(`#grpc`), 서로 다른 태그에 나뉜 다중 토큰(`#kafka spark`), 존재하지 않는 태그, `#`만 입력한 경우를 마이그레이션 전/후 결과와 비교해 독립적으로 검증 가능하다.

**Acceptance Scenarios**:

1. **Given** 태그를 가진 아티클들이 존재하는 상태, **When** 방문자가 `#` 뒤에 하나의 태그명 일부를 입력하면, **Then** 해당 태그를 대소문자 무시로 포함하는 모든 아티클이 원래 순서대로 나타난다.
2. **Given** 서로 다른 아티클이 서로 다른 태그 조합을 가진 상태, **When** 방문자가 공백으로 구분된 두 개 이상의 태그 토큰을 입력하면, **Then** 두 토큰을 모두 만족하는(서로 다른 태그에 나뉘어 있어도 무방한) 아티클만 나타난다.
3. **Given** 방문자가 `#`만 입력한 상태, **When** 그 외 아무 문자도 입력하지 않으면, **Then** 안내 힌트 대신 "No results found."가 표시된다.

### User Story 3 - 홈페이지 QuickSearch 필터 결과 동일성 (Priority: P3)

방문자가 홈페이지의 QuickSearch 프리셋 태그 버튼(GRPC / KAFKA+SPARK / OAUTH2+SECURITY 등)을 클릭하면, 마이그레이션 전과 동일한 카드 목록이 필터링되어 나타난다.

**Why this priority**: QuickSearch는 고정된 프리셋 태그 조합(최대 3개)만 다루므로 텍스트/태그 자유 검색보다 입력 공간이 훨씬 좁아 회귀 위험이 상대적으로 낮다.

**Independent Test**: 각 프리셋 버튼을 순서대로 클릭·해제하며 필터링된 카드 집합을 마이그레이션 전 결과와 비교하는 것만으로 독립적으로 검증 가능하다.

**Acceptance Scenarios**:

1. **Given** 홈페이지에 여러 태그를 가진 카드들이 표시된 상태, **When** 방문자가 하나의 프리셋 버튼을 클릭하면, **Then** 그 프리셋의 모든 태그를 AND로 만족하는 카드만 표시된다.
2. **Given** 프리셋 필터가 활성화된 상태, **When** 방문자가 같은 버튼을 다시 클릭하면, **Then** 필터가 해제되고 전체 카드가 다시 표시된다.

---

### Edge Cases

- 검색창이 완전히 비어 있을 때는 결과 대신 안내 힌트가 그대로 표시되는가? (매칭 엔진 교체와 무관하게 유지되어야 함)
- 아무 아티클과도 매치되지 않는 검색어를 입력했을 때 "No results found."가 정상 표시되는가?
- 태그에 밑줄(`_`)이나 점(`.`)처럼 특수 문자가 섞여 있을 때(예: `GO_1.21`), 그 특수 문자를 가로지르는 부분 문자열로 검색해도 여전히 매치되는가?
- 검색어에 아포스트로피, 하이픈, 느낌표 등 구두점이 포함된 제목/본문 문장을 가로지를 때도 매치가 누락되지 않는가?
- 제목과 본문에 동시에 매치되는 아티클이 본문 매치 그룹에 중복 표시되지 않고 제목 매치 그룹에만 한 번 표시되는가?

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 제목/본문 텍스트 검색에서 대소문자 무시 부분 문자열 매칭 결과를, 마이그레이션 이전 네이티브 구현과 동일한 결과 집합으로 제공해야 한다.
- **FR-002**: 제목 매치는 본문 매치보다 항상 상위에 정렬돼야 하며, 제목이 매치된 아티클은 본문 매치 여부와 무관하게 제목 매치 그룹에만 한 번 나타나야 한다(상호 배타).
- **FR-003**: 동일한 매치 그룹(제목/본문) 내부에서는 마이그레이션 이전과 동일한 원래 순서(발행일 내림차순)를 유지해야 한다.
- **FR-004**: 입력값이 `#`으로 시작하면 태그 검색 모드로 전환해야 한다.
- **FR-005**: 태그 검색에서 공백으로 구분된 각 토큰은 대소문자 무시 부분 문자열로 하나 이상의 태그와 일치해야 하고, 모든 토큰이 (서로 다른 태그에 나뉘어 있어도) 함께 만족돼야만 해당 아티클이 결과에 포함돼야 한다.
- **FR-006**: 태그 검색 결과는 랭킹 없이 마이그레이션 이전과 동일한 원래 순서를 유지해야 한다.
- **FR-007**: 입력값이 `#`만 있고 태그명이 없는 경우, 안내 힌트 대신 "No results found."를 표시해야 한다.
- **FR-008**: 검색 결과에서 일치 구간 하이라이트와 본문 발췌(매치 지점 앞뒤 문맥 노출)는 마이그레이션 이전과 동일하게 유지돼야 한다.
- **FR-009**: 홈페이지 QuickSearch 프리셋 버튼(1~3개 태그 조합)은 태그 검색과 동일한 AND·부분 문자열 규칙으로 카드 목록을 필터링해야 한다.
- **FR-010**: 검색 관련 키보드 상호작용(방향키 이동, 페이지 단위 이동, 처음/끝 이동, 선택, 닫기, 검색 열기 단축키)과 시각적 UI 요소는 마이그레이션 전후 동일하게 유지돼야 한다.
- **FR-011**: 매칭 엔진은 flexsearch 라이브러리를 실제 검색·필터링 수행에 사용해야 한다 — 라이브러리를 추가만 하고 기존 로직을 그대로 남겨두는 것은 이 요구사항을 만족하지 않는다.

### Key Entities

- **Search Index Entry**: 검색 대상이 되는 아티클 한 건 — 식별자, 제목, 검색용 순수 본문 텍스트, 태그 목록으로 구성됨. 홈페이지 노출 대상 아티클에서만 파생된다.
- **Search Query**: 방문자가 입력한 검색어 — 원본 입력값과, 그로부터 판별된 모드(텍스트/태그) 및 실제 매칭에 쓰이는 term으로 구성됨.
- **Search Result**: 검색 결과 항목 — 매치된 Search Index Entry와, 어디서 매치됐는지(제목/본문/태그 모드) 정보로 구성됨.
- **QuickSearch Preset**: 홈페이지 필터 버튼 하나 — 식별자, 표시 라벨, AND 매칭 대상 태그 목록(1~3개)으로 구성됨.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 현재 게시된 모든 아티클을 대상으로 임의의 텍스트 검색어를 입력했을 때, 반환되는 아티클 집합과 그 순서가 마이그레이션 이전과 100% 동일하다.
- **SC-002**: 현재 게시된 모든 아티클을 대상으로 임의의 단일/다중 태그 검색을 수행했을 때, 반환되는 아티클 집합과 그 순서가 마이그레이션 이전과 100% 동일하다.
- **SC-003**: 홈페이지의 모든 QuickSearch 프리셋 버튼을 각각 활성화했을 때, 필터링된 카드 집합이 마이그레이션 이전과 100% 동일하다.
- **SC-004**: 방문자는 검색 UI의 모양이나 조작 방식에서 마이그레이션 전후 차이를 인지할 수 없다 — 시각적 회귀나 키보드 조작 회귀가 하나도 없다.

## Assumptions

- 검색 대상 콘텐츠의 규모는 현재와 유사한 수십 편 단위를 가정하며, 대규모 트래픽/데이터셋에 대한 성능 최적화는 이번 범위에 포함하지 않는다.
- flexsearch가 기본 제공하는 오타 허용(fuzzy) 검색, 음성학적 매칭, 랭킹 고도화 등의 부가 기능은 이번 마이그레이션 범위 밖이며 이후 별도 기능으로 다룬다.
- 서버가 클라이언트로 전달하는 검색용 데이터 형태(직렬화 가능한 아티클/카드 배열)는 이번 작업으로 바뀌지 않는다 — 매칭 엔진 교체는 클라이언트 측 처리 방식의 변화이지 서버 데이터 계약의 변화가 아니다.
- `core/*.html` 정적 목업은 검색 UI 마크업 자체가 바뀌지 않으므로 이번 작업에서 갱신 대상이 아니다.
