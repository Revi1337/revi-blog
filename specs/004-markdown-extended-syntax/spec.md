## User Scenarios & Testing *(mandatory)*

### User Story 1 - 콜아웃으로 핵심 정보 강조 (Priority: P1)

블로그 저자가 옵시디언에서 작성한 아티클 원고에는 `> [!NOTE]`, `> [!WARNING]` 같은 콜아웃이 자주 포함된다. 저자는 이 콜아웃이 옵시디언에서 보던 것과 동일하게, 타입별로 구분되는 색상/아이콘을 가진 강조 박스로 블로그에도 그대로 나타나기를 기대한다. 독자는 이 박스를 통해 본문에서 특히 주의 깊게 봐야 할 정보(주의사항, 팁, 경고 등)를 한눈에 구분할 수 있어야 한다.

**Why this priority**: 이번 기능 요청의 출발점이자 가장 사용 빈도가 높을 것으로 예상되는 문법이며, 독자의 정보 습득 정확도에 직접적인 영향을 준다.

**Independent Test**: 콜아웃 문법만 포함된 마크다운 스니펫으로 빌드 후 렌더링 결과를 확인하는 것만으로 완전히 검증 가능 — 다른 5개 항목과 독립적으로 배포 가능.

**Acceptance Scenarios**:

1. **Given** 본문에 `> [!NOTE]\n> 내용` 이 있는 아티클, **When** 페이지를 렌더링하면, **Then** "NOTE" 타입에 대응하는 아이콘과 강조색을 가진 박스로 표시된다.
2. **Given** 본문에 `> [!WARNING]- 커스텀 제목\n> 내용` 이 있는 아티클, **When** 페이지를 렌더링하면, **Then** 박스는 기본적으로 접힌 상태이며 제목에는 "WARNING" 대신 "커스텀 제목"이 표시되고, 클릭하면 펼쳐진다.
3. **Given** 본문에 GitHub 스타일 `> [!IMPORTANT]` 가 있는 아티클, **When** 페이지를 렌더링하면, **Then** 옵시디언 콜아웃과 동일한 컴포넌트로 렌더링된다(별도 스타일 분기 없음).
4. **Given** 다크 모드와 라이트 모드, **When** 동일한 콜아웃을 각각 렌더링하면, **Then** 두 테마 모두에서 텍스트와 배경의 명도 대비가 읽기 충분한 수준으로 유지된다.

---

### User Story 2 - 수식이 포함된 기술 문서 정확히 표현 (Priority: P2)

기술 블로그 저자가 알고리즘 복잡도나 통계 지표를 설명할 때 `$O(n \log n)$` 같은 인라인 수식이나 `$$...$$` 블록 수식을 사용한다. 저자는 이 수식이 원본 텍스트(`$n^2$`)가 아니라 사람이 읽기 쉬운 수학 기호로 렌더링되기를 기대한다.

**Why this priority**: 콜아웃 다음으로 저작 빈도가 높은 문법이며, 정확히 렌더링되지 않으면 기술적으로 잘못된 정보를 전달하게 된다.

**Independent Test**: 인라인/블록 수식만 포함된 마크다운 스니펫으로 렌더링 결과를 확인하는 것으로 독립 검증 가능.

**Acceptance Scenarios**:

1. **Given** 본문에 `$O(n \log n)$` 이 있는 아티클, **When** 페이지를 렌더링하면, **Then** 원본 기호가 아닌 조판된 수학 표기로 인라인 표시된다.
2. **Given** 본문에 `$$\sum_{i=1}^{n} x_i$$` 블록이 있는 아티클, **When** 페이지를 렌더링하면, **Then** 별도 블록으로 가운데 정렬된 수식이 표시된다.
3. **Given** 다크 모드와 라이트 모드, **When** 동일한 수식을 각각 렌더링하면, **Then** 두 테마 모두에서 수식 기호가 배경과 충분한 대비로 읽힌다.

---

### User Story 3 - 본문 내 핵심 문구 시각적으로 강조 (Priority: P3)

저자가 본문 중 특정 단어나 문장을 `==하이라이트==`로 감싸 눈에 띄게 강조하고 싶어 한다. 독자는 형광펜으로 칠한 듯한 배경색이 적용된 텍스트를 통해 저자가 강조하고 싶었던 부분을 빠르게 파악할 수 있다.

**Why this priority**: 콜아웃/수식보다 사용 빈도가 낮고 대체 수단(볼드체)이 이미 존재하지만, 옵시디언 원고 이관 시 흔히 쓰이는 문법이라 지원 범위에 포함한다.

**Independent Test**: 하이라이트 문법만 포함된 마크다운 스니펫으로 렌더링 결과를 확인하는 것으로 독립 검증 가능.

**Acceptance Scenarios**:

1. **Given** 본문에 `이 부분이 ==가장 중요==하다` 가 있는 아티클, **When** 페이지를 렌더링하면, **Then** "가장 중요" 텍스트에만 강조 배경색이 적용된다.
2. **Given** 다크 모드와 라이트 모드, **When** 동일한 하이라이트를 각각 렌더링하면, **Then** 두 테마 모두에서 강조 배경과 텍스트 색이 충분한 대비를 유지한다.

---

### User Story 4 - 저작 시점의 메모를 독자에게 노출하지 않기 (Priority: P4)

저자가 옵시디언에서 초안을 작성하며 `%% TODO: 통계 출처 확인 %%` 같은 작업용 메모를 본문 중간에 남겨둔다. 이 메모는 저자 자신을 위한 것이며 발행된 블로그 글에는 절대 노출되면 안 된다.

**Why this priority**: 노출 시 저자의 사적인 작업 메모가 독자에게 그대로 보이는 신뢰도 문제로 이어질 수 있으나, 발생 빈도 자체는 다른 항목보다 낮다.

**Independent Test**: 주석 문법만 포함된 마크다운 스니펫을 렌더링해 해당 텍스트가 최종 HTML에 전혀 나타나지 않음을 확인하는 것으로 독립 검증 가능.

**Acceptance Scenarios**:

1. **Given** 본문에 `공개 문장. %%비공개 메모%% 다음 공개 문장.` 이 있는 아티클, **When** 페이지를 렌더링하면, **Then** "비공개 메모" 텍스트는 렌더링 결과 HTML 어디에도 존재하지 않고 앞뒤 공개 문장은 자연스럽게 이어진다.

---

### User Story 5 - 특정 섹션으로 바로 이동하는 링크 공유 (Priority: P5)

독자가 아티클의 특정 소제목(예: h4 레벨의 세부 벤치마크 섹션)을 다른 사람에게 공유하고 싶을 때, 그 소제목까지 바로 스크롤되는 URL을 얻을 수 있어야 한다. 현재는 h2/h3 레벨의 제목에만 이런 링크가 가능하다.

**Why this priority**: 콘텐츠 접근성을 개선하지만 필수 기능은 아니며, 다른 항목들과 달리 순수 부가 기능이라 가장 낮은 우선순위로 둔다.

**Independent Test**: h1, h4~h6 레벨 헤딩이 포함된 아티클에서 해당 헤딩까지의 URL 딥링크가 정확히 동작하는지 확인하는 것으로 독립 검증 가능.

**Acceptance Scenarios**:

1. **Given** 본문에 h4 레벨 소제목이 있는 아티클, **When** 페이지가 렌더링되면, **Then** 해당 소제목으로 스크롤 이동 가능한 링크가 존재한다.
2. **Given** h2/h3 레벨의 목차(TOC), **When** 페이지가 렌더링되면, **Then** TOC 목록에는 기존과 동일하게 h2/h3만 표시되고 h1·h4~h6 헤딩으로 목록이 늘어나지 않는다.

---

### User Story 6 - 옵시디언 원고의 접이식 섹션이 시각적으로 자연스럽게 표시 (Priority: P6)

저자가 옵시디언 원고에 접기/펼치기 가능한 세부 설명 섹션을 사용했을 때, 블로그에서도 이 섹션이 기존 디자인 시스템의 톤(다크/라이트 배색, 폰트)과 어울리게 표시되어야 한다.

**Why this priority**: 기능 자체는 이미 동작하고 있어 신규 위험이 가장 낮으며, 남은 작업은 시각적 다듬기뿐이다.

**Independent Test**: 접이식 섹션이 포함된 아티클을 다크/라이트 모드 각각에서 렌더링해 디자인 일관성을 눈으로 확인하는 것으로 독립 검증 가능.

**Acceptance Scenarios**:

1. **Given** 본문에 접이식 섹션이 있는 아티클, **When** 다크 모드와 라이트 모드에서 각각 렌더링하면, **Then** 두 테마 모두 기존 본문 디자인 톤과 자연스럽게 어울리는 접기/펼치기 UI가 표시된다.

### Edge Cases

- 콜아웃 타입이 지원 목록에 없는 미상의 값(예: `[!UNKNOWN]`)이면 어떻게 되는가? → 알 수 없는 타입은 가장 기본적인 콜아웃 스타일(note 취급)로 표시하고 타입 라벨은 입력된 원문 그대로 노출한다.
- 콜아웃 blockquote 안에 리스트나 코드블록처럼 다른 마크다운 요소가 중첩되어 있으면 어떻게 되는가? → 콜아웃 박스 내부에서도 정상적으로 렌더링되어야 한다.
- 하이라이트 문법이 코드 스팬이나 코드 블록 안에서 사용되면(예: `` `==a==` ``) 어떻게 되는가? → 코드로 취급되어 하이라이트로 변환되지 않고 원문 그대로 표시된다.
- 주석(`%%...%%`)이 닫히지 않고 파일 끝까지 이어지면 어떻게 되는가? → 열린 주석 시작 지점부터 파일 끝까지 전부 비공개로 취급해 제거한다.
- 수식 구문에 오류가 있으면(예: 괄호 불일치) 어떻게 되는가? → 페이지 전체가 깨지지 않고, 해당 수식 위치에 원본 텍스트를 그대로 표시한다.
- 기존 7개 아티클에는 이번 6개 신규 문법이 전혀 쓰이지 않는데, 이 아티클들의 기존 렌더링 결과가 이번 변경으로 달라지는가? → 달라지지 않아야 한다(회귀 없음).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 blockquote가 `[!TYPE]` 패턴으로 시작하면 이를 일반 인용구 대신 타입별로 구분되는 콜아웃 박스로 렌더링해야 한다.
- **FR-002**: 시스템은 최소 note, tip, warning, danger, info, success, question, bug, example, quote 10종의 콜아웃 타입을 각각 구분되는 아이콘/강조색으로 지원해야 한다.
- **FR-003**: 시스템은 GitHub Alerts 5종(NOTE, TIP, IMPORTANT, WARNING, CAUTION)을 동일한 콜아웃 컴포넌트로 매핑해 렌더링해야 한다.
- **FR-004**: 시스템은 콜아웃 타입 뒤에 `-`가 붙으면 기본 접힘, `+`가 붙으면 기본 펼침 상태로 렌더링해야 하며, 독자가 클릭해 상태를 전환할 수 있어야 한다.
- **FR-005**: 시스템은 콜아웃 타입 뒤에 이어지는 텍스트를 커스텀 제목으로 사용해야 하며, 텍스트가 없으면 타입명을 기본 제목으로 사용해야 한다.
- **FR-006**: 시스템은 인라인 수식(`$...$`)과 블록 수식(`$$...$$`)을 사람이 읽을 수 있는 조판된 수학 표기로 렌더링해야 한다.
- **FR-007**: 시스템은 `==...==`로 감싼 텍스트를 시각적으로 강조된 하이라이트로 렌더링해야 한다.
- **FR-008**: 시스템은 `%%...%%`로 감싼 텍스트를 최종 렌더링 결과에서 완전히 제거해야 하며, 어떤 형태로도(HTML 주석 포함) 출력에 남기지 않아야 한다.
- **FR-009**: 시스템은 h1~h6 전체 레벨의 헤딩에 딥링크 가능한 고유 앵커를 부여해야 한다.
- **FR-010**: 시스템은 목차(TOC) 목록에는 기존과 동일하게 h2/h3 레벨의 헤딩만 포함해야 한다.
- **FR-011**: 시스템은 접이식 섹션(details/summary)이 다크 모드와 라이트 모드 각각에서 기존 본문 디자인과 시각적으로 일관되게 표시되도록 해야 한다.
- **FR-012**: 시스템은 이번에 추가되는 6개 문법 모두를 다크 모드와 라이트 모드 양쪽에서 읽기 충분한 명도 대비로 표시해야 한다.
- **FR-013**: 시스템은 이번 변경 이전에 발행된 기존 아티클들의 렌더링 결과를 이번 변경으로 인해 달라지게 해서는 안 된다.
- **FR-014**: 시스템은 지원 목록에 없는 콜아웃 타입이 입력되면 기본 스타일로 대체 표시하되 입력된 타입 라벨 원문은 유지해야 한다.
- **FR-015**: 시스템은 수식 구문 오류가 있어도 페이지 전체 렌더링이 실패하지 않고, 해당 수식 위치에 원본 텍스트를 그대로 표시해야 한다.

### Key Entities

- **콜아웃(Callout)**: 본문 중 특정 유형(주의/팁/경고 등)의 정보를 강조하는 박스. 타입, 제목(커스텀 또는 기본), 접힘 상태, 본문 내용을 속성으로 가진다.
- **헤딩 앵커**: 문서 내 특정 위치로 이동하기 위한 식별자. 헤딩 레벨(h1~h6), 고유 id, 소속 아티클을 속성으로 가진다.
- **목차 항목(TOC Item)**: 아티클 상단/사이드에 노출되는 탐색 목록의 항목. h2/h3 레벨 헤딩만을 대상으로 하며 헤딩 앵커의 부분집합이다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 옵시디언에서 작성된 원고를 별도 수정 없이 붙여넣었을 때, 이번 6개 문법(콜아웃/수식/하이라이트/주석/전헤딩앵커/접기스타일링) 모두가 원고 작성자가 옵시디언에서 본 것과 동일한 의도로 블로그에 표시된다.
- **SC-002**: 10종의 콜아웃 타입과 GitHub Alerts 5종 별칭 모두 다크/라이트 두 테마에서 각각 시각적으로 구분 가능하다(20개 조합 전수 확인).
- **SC-003**: 저자가 남긴 비공개 작업 메모(`%%...%%`)가 발행된 페이지의 HTML 소스 어디에도 노출되지 않는 비율이 100%다.
- **SC-004**: 기존에 발행된 7개 아티클의 렌더링 결과(HTML 출력)가 이번 변경 적용 전후로 동일하다.
- **SC-005**: h1, h4~h6 레벨 헤딩을 포함한 아티클에서, 해당 헤딩으로의 딥링크 URL 접속 시 100% 정확한 위치로 스크롤 이동한다.

## Assumptions

- 콜아웃 타입 집합은 옵시디언 기본 제공 타입(note, tip, warning, danger, info, success, question, bug, example, quote)을 기준으로 하며, 사용자 정의 커스텀 타입 추가는 이번 범위에 포함하지 않는다.
- 수식 렌더링은 표준 LaTeX 수학 표기 문법을 기준으로 하며, 옵시디언/GitHub에서 통용되는 범위를 벗어나는 고급 LaTeX 패키지 문법 지원은 범위 밖으로 가정한다.
- `#태그` 인라인 문법과 `^블록ID` 참조 문법은 이번 범위에서 명시적으로 제외한다(프론트매터 tags와의 책임 중복, 위키링크 부재로 인한 반쪽 기능이 각각의 사유).
- 각주(`[^1]`)는 이미 지원되고 있으므로 이번 범위에 포함하지 않는다.
- 검증은 신규 작성되는 검증용 아티클/스니펫과 실제 브라우저 렌더링 확인으로 이루어지며, 별도 자동화 테스트 스위트 신설 여부는 이번 스펙의 범위 밖이다.
