# Feature Specification: Markdown 기반 아티클 콘텐츠 파이프라인

**Feature Branch**: `003-markdown-article-pipeline`

**Created**: 2026-07-20

**Status**: Draft

**Input**: User description: "Markdown 기반 아티클 콘텐츠 파이프라인 구축 — 현재 lib/data/articles.ts에 하드코딩된 Article[] 배열(HTML 문자열 본문, __CODE_BLOCK__/__METRICS__ 플레이스홀더)을 실제 파일시스템 기반 .md 콘텐츠(프론트매터 + 본문)로 교체. Astro의 파일 기반 마크다운 + frontmatter + remark/rehype 파이프라인 아키텍처를 참고 레퍼런스로 삼아 Next.js 위에서 동등한 패턴을 재현. 코드 블록 라인 하이라이트(`{2-3,10}` 문법) 지원, 다크/라이트 테마 동시 대응 필수."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 콘텐츠 작성자가 마크다운 파일만으로 새 아티클을 발행한다 (Priority: P1)

콘텐츠 작성자(이 프로젝트를 운영하는 개발자 본인)가 코드를 수정하지 않고, 지정된 폴더에 프론트매터가 포함된 마크다운 파일 하나를 추가하는 것만으로 새 아티클이 홈 목록과 상세 페이지에 나타나야 한다.

**Why this priority**: 지금은 새 글을 추가하려면 `lib/data/articles.ts`의 TS 배열에 HTML 문자열을 손으로 이어붙여야 한다. 이 마찰을 없애는 것이 이번 기능의 핵심 목적이며, 이것 없이는 나머지 요구사항(TOC 자동 생성, 코드 하이라이트 등)이 의미가 없다.

**Independent Test**: 지정된 콘텐츠 폴더에 프론트매터(제목, 발행일, 카테고리, 태그 등)를 갖춘 `.md` 파일 하나를 추가하고 개발 서버를 재시작(또는 재빌드)했을 때, 홈 페이지 카드 목록과 해당 slug의 상세 페이지에 그 글이 정상적으로 노출되는지로 검증한다.

**Acceptance Scenarios**:

1. **Given** 콘텐츠 폴더가 비어있지 않은 상태, **When** 프론트매터와 본문을 갖춘 새 `.md` 파일을 추가하면, **Then** 홈 페이지 카드 목록에 해당 글이 제목·발행일·썸네일과 함께 나타난다.
2. **Given** 새로 추가한 `.md` 파일의 slug로 상세 페이지에 접근하면, **Then** 본문이 마크다운 원문 그대로의 구조(제목 위계, 목록, 문단)를 유지한 HTML로 렌더링된다.
3. **Given** 프론트매터에 필수 필드(제목, 발행일 등) 중 하나가 누락된 `.md` 파일, **When** 빌드를 실행하면, **Then** 어떤 파일의 어떤 필드가 누락되었는지 식별 가능한 오류 메시지와 함께 빌드가 실패한다(깨진 아티클이 조용히 배포되지 않는다).

---

### User Story 2 - 독자가 코드 블록에서 특정 줄이 강조된 것을 본다 (Priority: P2)

아티클을 읽는 독자가 코드 예제가 포함된 글을 열었을 때, 저자가 지정한 특정 줄(또는 범위)이 시각적으로 강조되어 있어 어디에 주목해야 하는지 바로 알 수 있어야 한다.

**Why this priority**: 이 프로젝트의 아티클은 시스템 아키텍처/코드 예제 중심 콘텐츠(예: 분산 시스템, PostgreSQL 인덱싱)라 코드 하이라이트가 읽기 경험에 직접적인 가치를 준다. 다만 User Story 1(콘텐츠가 파일에서 로드되는 것) 없이는 시도할 수 없으므로 P2.

**Why this priority**: 콘텐츠 파이프라인 자체(P1)가 선행되어야 검증 가능한 기능이라 두 번째 우선순위.

**Independent Test**: 라인 하이라이트 지시자를 포함한 코드 블록을 가진 `.md` 파일 하나를 렌더링해서, 지정된 줄에만 강조 스타일이 적용되고 나머지 줄은 그대로인지 확인한다. 다크 테마와 라이트 테마 각각에서 강조색이 배경과 충분한 대비를 갖는지 육안으로 확인한다.

**Acceptance Scenarios**:

1. **Given** 특정 줄 번호(예: 2~3번째 줄)를 강조하도록 지정된 코드 블록, **When** 아티클 상세 페이지를 렌더링하면, **Then** 지정된 줄에만 강조 배경이 적용되고 나머지 줄은 일반 스타일로 표시된다.
2. **Given** 동일한 아티클, **When** 다크 테마와 라이트 테마를 각각 켜고 확인하면, **Then** 두 테마 모두에서 강조된 줄과 일반 줄이 명확히 구분되고 코드 텍스트의 가독성(대비)이 유지된다.
3. **Given** 라인 하이라이트 지시자가 없는 일반 코드 블록, **When** 렌더링하면, **Then** 강조 없이 기존과 동일하게 정상 표시된다(하이라이트 미지정이 오류를 일으키지 않는다).

---

### User Story 3 - 독자가 목차(TOC)를 통해 긴 아티클을 탐색한다 (Priority: P3)

독자가 긴 아티클을 읽을 때, 본문의 제목 구조로부터 자동 생성된 목차를 통해 원하는 섹션으로 바로 이동할 수 있어야 한다.

**Why this priority**: 현재도 목차 기능 자체는 존재하지만 수동으로 배열을 작성해야 한다. 자동화는 유지보수성 문제(오탈자, 누락 헤딩)를 없애주지만 독자 체감 가치는 P1/P2보다 낮으므로 P3.

**Independent Test**: 여러 개의 H2/H3 제목을 가진 `.md` 파일을 렌더링했을 때, 수동 설정 없이 목차 항목이 제목 순서·위계 그대로 생성되고, 각 항목 클릭 시 본문의 해당 위치로 스크롤 이동하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** H2 제목 3개와 그 아래 H3 제목 1개를 포함한 마크다운 본문, **When** 상세 페이지를 렌더링하면, **Then** 목차에 4개 항목이 본문 순서와 위계 그대로 나타난다.
2. **Given** 렌더링된 목차, **When** 목차 항목 하나를 클릭하면, **Then** 본문의 해당 제목 위치로 이동한다.
3. **Given** 본문에 제목이 하나도 없는 짧은 마크다운 파일, **When** 렌더링하면, **Then** 목차 영역이 비어있거나 숨겨지고 오류 없이 페이지가 정상 표시된다.

---

### Edge Cases

- 같은 파일명(slug)을 가진 마크다운 파일이 두 개 존재하면 어떻게 되는가? (빌드 실패로 처리하고 충돌 파일을 명시해야 한다)
- 프론트매터에 썸네일이 없는 글은 어떻게 표시되는가? (기존 `DEFAULT_THUMBNAIL` 폴백을 그대로 재사용)
- 본문에 마크다운 문법으로 표현할 수 없는 레이아웃(예: 기존 `__METRICS__` 성능 지표 카드)이 필요한 글은 어떻게 처리하는가?
- 코드 블록의 라인 하이라이트 지시자가 실제 코드 줄 수를 벗어난 범위(예: 5줄짜리 코드에 `{10}` 지정)를 가리키면 어떻게 되는가? (조용히 무시하거나 빌드 경고를 낸다 — 페이지 렌더링 자체는 실패하지 않아야 한다)
- 기존 4개 하드코딩 아티클을 마이그레이션하는 도중 일부 필드(예: `prev`/`next` 참조 slug)가 실제 존재하지 않는 글을 가리키던 경우는 어떻게 하는가? (발행일 기준 자동 계산으로 대체되므로 더 이상 수동 참조 오류가 발생하지 않는다)

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 지정된 콘텐츠 폴더 안의 `.md` 파일을 아티클 콘텐츠의 단일 소스(source of truth)로 사용해야 하며, 코드 안에 아티클 본문이 하드코딩되어서는 안 된다.
- **FR-002**: 시스템은 각 마크다운 파일의 프론트매터로부터 제목, 카테고리, 발행일, 태그, 썸네일(선택) 등 아티클 메타데이터를 읽어야 한다.
- **FR-003**: 시스템은 마크다운 본문을 파싱하여 기존과 동등한 구조(제목, 문단, 목록, 코드 블록)를 유지하는 HTML로 변환해야 한다.
- **FR-004**: 시스템은 본문 안의 제목(H2/H3)으로부터 목차 항목을 자동으로 생성해야 하며, 수동으로 목차를 별도 작성할 필요가 없어야 한다.
- **FR-005**: 시스템은 코드 블록에 대해 특정 줄(단일 줄 및 범위)을 지정해 시각적으로 강조하는 기능을 지원해야 하며, 다크/라이트 테마 양쪽에서 강조와 비강조 영역이 충분한 대비로 구분되어야 한다.
- **FR-006**: 시스템은 프론트매터에 필수 메타데이터가 누락된 경우, 어떤 파일의 어떤 필드가 문제인지 식별 가능한 오류로 빌드를 실패시켜야 한다(깨진 콘텐츠가 조용히 배포되지 않아야 한다).
- **FR-007**: 시스템은 아티클 간 이전글/다음글 이동을 발행일 순서 등 명시적이고 일관된 규칙에 따라 자동으로 계산해야 하며, 더 이상 수동으로 참조 slug를 지정할 필요가 없어야 한다.
- **FR-008**: 시스템은 기존에 하드코딩되어 있던 4개 아티클(고동시성 분산 시스템, PostgreSQL 인덱싱, Kafka Streams vs Spark, OAuth2 보안 감사)의 콘텐츠를 유실 없이 마크다운 파일로 옮겨야 한다.
- **FR-009**: 홈 페이지의 아티클 카드 목록과 상세 페이지는 이 새로운 콘텐츠 소스를 사용하도록 전환되어야 하며, 사용자 관점에서 기존과 동일한 화면 구성(레이아웃, 다크/라이트 테마)이 유지되어야 한다.
- **FR-010**: 시스템은 마크다운 본문 안에서 표준 문단/제목/코드로 표현하기 어려운 보강 콘텐츠(예: 성능 지표 카드류의 강조 블록)를, 저자가 본문 흐름 안 원하는 위치에 삽입할 수 있는 커스텀 블록 문법으로 표현할 방법을 제공해야 한다(프론트매터 필드가 아닌 본문 내 표기). 이 커스텀 블록은 파싱되어 기존 `MetricCard[]`와 동등한 데이터로 렌더링되어야 한다.

### Key Entities *(include if feature involves data)*

- **Article Content File**: 파일시스템에 저장된 마크다운 파일 한 개. 프론트매터(구조화된 메타데이터)와 본문(마크다운 텍스트)으로 구성되며, 파일 하나가 아티클 하나에 대응한다.
- **Article Metadata**: 프론트매터로부터 추출되는 구조화된 정보 — 제목, 카테고리, 발행일, 수정일(있는 경우), 태그, 썸네일(있는 경우), 예상 읽기 시간.
- **Table of Contents Entry**: 본문의 제목으로부터 자동 파생되는 항목으로, 제목 텍스트·위계(순서)·본문 내 위치 참조를 가진다.
- **Code Highlight Directive**: 코드 블록에 부여되는 강조 대상 줄 지정(단일 줄 또는 범위의 조합).
- **Article Navigation Reference**: 한 아티클의 이전글/다음글을 가리키는 관계로, 발행일 등 명시적 규칙에 따라 자동 산출된다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 콘텐츠 작성자가 코드를 수정하지 않고 새 마크다운 파일 하나만 추가해서 새 아티클을 발행할 수 있다.
- **SC-002**: 기존 4개 아티클이 마이그레이션 후에도 내용 유실 없이 동일한 정보(제목, 본문, 코드 예제, 태그, 날짜)로 노출된다.
- **SC-003**: 코드 예제가 포함된 아티클을 읽는 독자의 100%가 다크·라이트 테마 어느 쪽에서 보더라도 저자가 지정한 강조 줄을 시각적으로 식별할 수 있다.
- **SC-004**: 제목이 2개 이상 포함된 아티클의 100%에서 목차가 수동 개입 없이 본문 구조와 정확히 일치하게 생성된다.
- **SC-005**: 프론트매터 필수 필드가 누락된 콘텐츠는 100% 빌드 단계에서 걸러지며, 손상된 상태로 배포되는 사례가 0건이다.

## Assumptions

- 콘텐츠는 여러 저자가 동시에 협업하는 구조가 아니라, 이 블로그를 운영하는 1인 개발자가 로컬에서 파일을 추가/수정하는 워크플로우를 전제로 한다.
- 콘텐츠 파일은 빌드/배포 시점에 정적으로 처리되며, 런타임에 외부 사용자가 마크다운을 업로드하거나 실시간으로 콘텐츠를 수정하는 기능은 이번 범위에 포함되지 않는다.
- 기존 `Article`/`BlogCardData` 타입이 표현하던 정보(카테고리, 태그, 읽기 시간, 썸네일 등)는 그대로 유지되며, 이번 기능은 그 데이터의 출처(source)만 하드코딩 배열에서 파일시스템 기반으로 바꾼다.
- CMS 연동, 외부 API 기반 콘텐츠 관리, Astro 프레임워크 자체의 도입은 이번 범위에서 제외한다 — Astro는 아키텍처 패턴의 참고 레퍼런스로만 사용한다.
- 코드 블록 라인 하이라이트 문법은 업계에서 널리 쓰이는 `{n,n-n}` 표기(Obsidian, Astro Expressive Code 등과 동일한 관례)를 따른다.
